# st-registry で作業するときの決まり

**指針は GUIDELINES.md。** ここには「どう進めるか」だけを書く。

## 位置づけ

不動産セキュリティトークン(ST)の**記述**を、機械可読な形でチェーンに置く試作。

主張は 1 つだけ。**決済を自動化するほど、記述の標準化が要る。**
同じ稼働率 100% でも、分母が宣言されていなければコントラクトは評価を実行できない。
拒否は不具合ではなく、正しい振る舞いである。

発端は 2026-08-26 の調査。目論見書は数値に必ず根拠と基準時点を添える
(「延床面積（登記簿）」「稼働率（面積ベース）」)が、運用サイトではそれが落ちる。

## 終わったと言う前に

### 1. 画面を実際に開く

`toBeVisible()` は透明でも通る。**Playwright で撮って Read で開く。**
実際、最初の撮影では **port 3000 で動いていた別プロジェクト(genji-x)が写っていた。**
テストが通ることと、見て正しいことは別。

### 2. チェーンから返った値かどうかを疑う

画面の数字がハードコードでないことを、`cast call` で別経路から突き合わせる。
「それらしい値が出た」で終わらせない。

### 3. 載せてよいデータかを毎回確かめる

**指針は「個人データをチェーンに載せるな」**(平文も暗号化もハッシュもだめ)。
建物の事実は個人データではないので対象外。ただし次の 2 つは別問題として残る。

- **商業上の機密**(賃料など。目論見書で「非開示」とされる項目)
- **消せない**こと。間違った値を置いたら取り消せない

**創作した数値を実在の物件名で置かない。** 一度そうしかけて止めた。
非開示の賃料に創作値を当てると、チェーン上で実データと取り違えられる。

### 4. 秘匿EVMは個人データの解決策ではない

Sapphire は**商業機密**を隠せる。だが指針は「暗号化してもだめ」と明言している。
**賃料は置いてよい。賃借人の情報は置いてはいけない。**

## 踏んだ落とし穴

### Oasis Sapphire ではコンストラクタに string を渡せない

配備トランザクションが status 0 で失敗する。`bytes32`・mapping への書き込み・
引数なしは成功する。`name()` の読み出しも `invalid code` で落ちた。
**可変長の文字列が絡むと不安定。** 表示名はチェーンに置かず画面側で持つ。
公式ドキュメントには見当たらなかった(2026-08-26 実測)。

### Pontus-X は組織登録が要る

法人名 + 登録番号(vatID / EORI / EUID / LEI)と Trust Anchor の審査。
**承認されて初めて faucet が使える。**
秘匿を確かめたいだけなら **Oasis Sapphire Testnet を直接使う**(登録不要、公開 faucet)。
Pontus-X = Sapphire + Ocean + Gaia-X の統治。登録が要るのは統治の層だけ。

### zsh では `$a` が単語分割されない

`for a in "x y z"; do cmd $a` は bash と違って 1 引数になる。`${=a}` を使うか、
素直に 1 行 1 コマンドで書く。

### expectRevert の直後に外部呼び出しをしない

`vm.expectRevert(); c.f(reg.KEY(), ...)` は `reg.KEY()` に掛かってしまう。
引数は先に変数へ取り出す。

## 秘密の扱い

秘密鍵は **1Password にだけ置く**。`op read` で実行時に取り出し、使い終わったら `unset`。
`.env.local` に入ってよいのは公開値だけ(チェーン名、RPC URL、コントラクトアドレス)。
