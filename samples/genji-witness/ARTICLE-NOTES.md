## ★ チェーンに何が載って、何が載らないか

いちばん誤解される。「Ocean に載せた」「チェーンに刻んだ」を曖昧に流すと、
読者は本文が載ったと思う。

- 本文 5,871,913 バイト → チェーンには載らない（**9 万分の 1** の root 64 バイトだけ）
- 載らない理由を数字で: calldata は 1 バイト 16 ガス → 約 9,400 万ガス。
  ブロック上限 3,000 万の **3 倍以上**で、1 トランザクションに収まらない
- 実際に送った calldata 452 バイトを **全ワード注釈つき**で出す
  （関数の指紋 4 バイト / bytes32 が 2 つ / uint64 / uint32 /
  文字列は「何バイト目から」を先に書く形）
- ログの topic と data の分かれ方。**topic は 3 個まで**という制約
- 「誰が刻んだか」を topic に入れた理由 → 後から第三者の人数を数えるため
- 状態変数を 1 つも持たない設計と、その代償
  （`latestSourceUri()` が無い＝読む側が全部読んで判断する）

## ★ CAR ファイルとは何か

- zip/tar との違い: **中身の一つひとつに CID が付いている**
- 圧縮しない理由（圧縮すると CID が変わる）
- 構造は単純: ヘッダの後は `[長さ][CID][中身]` の繰り返しだけ。実物の 16 進を出す
- ヘッダの `roots` = 読み始める入口。
  実測で `e7214a3c…b57879` が自分のディレクトリ CID の digest と一致した
- ブロック数 63 の検算: 単一ブロック 50 + 分割ファイル 4×3 + ディレクトリ 1
- なぜ CAR で渡すか: ファイル単位で上げるとサービス側が DAG を組み直し、
  **確定させたディレクトリ CID が変わる**ことがある

## ★ 券（datatoken）は閲覧を制限しない

読者の直感（「NFT を買った人だけが読める」）と実物が違う。

- 発行した DDO の実物を出す: `flags 0x00` / `files: ""` /
  `serviceEndpoint` は公開の GitHub Pages / `license: CC0-1.0`
- Ocean の本来の設計では **Provider というサーバが門番**をする。
  暗号ではない。**券は鍵ではない**
- 元の URL が公開なら Ocean を通さず直接取れる。
  逆に Provider が止まれば券があっても取れない
- Enterprise テンプレートは 1 トランザクションで
  「出す→記録する→焼く」。**持てないものは鍵になりえない**
- 実測: Sepolia の他人の資産 3 件は全部 `flags 0x02`（暗号化）で
  `decryptorUrl` 依存。そのノードが消えたら永久に読めない

## ★ GitHub での公開と、このカタログの違い

正直に書く。今回の出し方だと差分は 3 つで、うち 2 つはまだ「できる」だけ。

| | GitHub | カタログ |
|---|---|---|
| 本文が読める | ✓ | GitHub を指しているだけ |
| 版が固定される | ✓ | ✓ |
| 利用が公開の記録に残る | ✗ | **✓** |
| 第三者が書き込める | ✗ | **✓**（GitHub は持ち主しか書けない） |
| 本文が消えない | ✗ | ✗ → IPFS で埋めた |

- 注文は「利用の**検出**」ではなく「利用の**申告**」。引用と同じ構造。
  違うのは**申告を受け取る組織を信用しなくてよい**こと
- 券が要らないので、GitHub から直接読む人は数えられない（強制力がない）

## 署名を自分で書いた話

- ここまで鍵を持っていなかった（anvil の `eth_sendTransaction` に頼っていた）
- 公開チェーンにその窓口は無い。publicnode も Infura も持たない
- 落とし穴は「動かない」ではなく「**静かにずれる**」形で出る:
  - 数の 0 は空のバイト列。`0x00` ではない。**nonce 0 のときだけ**ずれる
  - low-s に正規化する（EIP-2）。忘れると署名は有効なのに**別人になる**
- 突き合わせた相手: RLP 仕様の公開値 / RFC 6979 の secp256k1 ベクトル /
  `cast mktx` と **バイト単位で 7 通り**（nonce 0・value 0・コントラクト作成含む）
- `cast` と比較できるのは RFC 6979 が乱数を使わないおかげ
- **一定時間の実装ではない**と明記する。本番の資金には使わない

## 「消せる」の区別

| | 消せるか | 費用 |
|---|---|---|
| GitHub | 消せる | 無料（誰かが払っている） |

## ★ コントラクトのイベントは全部読み出せて、誰でも見られる

ユーザーが「知らなかった、発見だった」と言った点。読者も同じはず。

- コントラクトのアドレスが分かれば、**そこが出したイベントを全部**引ける
  (`eth_getLogs` に address を渡すだけ)。許可も鍵も要らない
- Etherscan のコントラクトページにも一覧が出る。ブラウザだけで辿れる
- **`CorpusAnchor` は状態変数を 1 つも持っていない**のに、
  何がいつ誰によって刻まれたかの全履歴が読める。

- だから「上書き」という操作が存在しない。
  同じ root に sourceUri 違いの記録が 2 つ並ぶ (今日実際にそうなった)
- 代償: 「いまの正解はどれか」を聞く窓口が無い。読む側が全部読んで判断する
- これがカタログ (10-catalog.mjs) が成り立つ理由でもある。
  索引サーバが 503 でも、ログは誰でも読めるので、カタログは作り直せる

## ブロックとコントラクトの関係 (大学生向けの説明として)

- ブロックは「作った」のではない。ネットワークが約 12 秒ごとに作り続けていて、
  そこに自分のトランザクションを**入れてもらった**
- 実測: 自分の 5 件が入ったブロックには 90〜245 件が入っていて、
  **うち自分のものは 1 件だけ**。残りは世界中の他人のもの
- 5 つのブロックに分かれたのは 1 件ずつ取り込みを待ったから
- 11568903 と 11569036 の間に 133 ブロック。
  IPFS の作業をしていた 29 分の間に、他人の分だけが積まれた (1 ブロック 12.9 秒)
- **コントラクトはブロックの中には無い。** 状態の側にある。
  ブロック 11568901 のトランザクションで「生まれた」が、
  以後は住所 0x8197bd… に存在している
- 家に例えると、ブロックは登記の記録、コントラクトは建った家

## 身元の問題 (オラクル問題との関係)

- 鍵 0xA787b128… には「中村覚である」「東大の一員である」という裏づけが無い
- オラクル問題の一種ではある (チェーンは外の世界の事実を確かめられない)
- ただし身元には抜け道がある。**本人が既に持っている場所から宣言できる**
- **双方向リンク**が要る:
  - チェーン → 現実: `sourceUri` に GitHub の URL (もう入っている)
  - 現実 → チェーン: サイト側に address を書く (まだ無い) ← 片方向では成立しない
- さらに署名つき宣言文を置くと「サイトを書き換えられる人」に加えて
  「鍵を実際に持っている人」まで示せる
- EAS は「その第三者を誰が信用するのか」が一段ずれるだけ
- **重要な区別**:
  - 「この版は改竄されていない」→ 身元は要らない。独立した N 人で足りる。匿名でも効く
  - 「東大史料編纂所が公式に認めた版」→ 身元が要る。誰が言ったかが主張の中身
  - CorpusAnchor が担うのは前者

## ★ Etherscan の読み方

- **data NFT と datatoken は別アドレス。** 1 回の取引でできたので同じものに見える
- data NFT のページのコードは **45 バイトしかない**。EIP-1167 最小プロキシで、
  実体は委譲先 `0x9c9ee07b…` (Ocean の ERC721Template)。だから Contract タブに
  ソースが出ない
- **「1 of ○○」の 1 は個数ではなく tokenId (背番号)。** ERC-721 は
  `ownerOf(1)` で持ち主を引く。ERC-20 の同じ位置の数字は本当に個数で、意味が違う
- 発行は `Transfer(from=0x000…000)` で表す。NFT に mint 専用のイベントは無い
- トークンページの `#transactions` は**移転しか出ない**。DDO の書き込みは
  移転ではないので出てこない。アドレスページの Events タブで見る
- `?a=<address>` はその一覧をそのアドレスで絞り込む指定
- `contract_deployed: null` は「宛先を指定した呼び出しだから」。
  中で作られたコントラクトはこの欄に出ず、ログを見ないと分からない
- datatoken のページは **Holders が空**に見える。`totalSupply 0`。
  壊れているのではなく、券が注文の瞬間に出て同じ取引で焼かれる設計だから

## ★ 取り消せない記録に、他人の氏名を載せられない

今日いちばん重い論点。技術ではなく資料の扱いの問題。

- DDO の `author` に「中村 覚」と**手で書いていた**。TEI ヘッダを 54 帖すべて集計したら、
  実際は **5 名の分担**だった（翻刻 3 名 / TEI 化 1 名 / 助言 1 名）。
  1 人だけを author にしていたのは学術資料として不正確。CC0 でも帰属表示は意味を持つ
- ではチームの 5 名を載せればよいかというと、**載せられない**。
  **チェーンへの記録は取り消せない**ので、本人の同意なく他人の氏名を永久に公開できない
- 結果、「資料は複数名の成果なのに、記録できるのは 1 人の名前だけ」という状態が生まれる
- 逃げ道は、**氏名を載せず、人数と『どこを見れば分かるか』を書く**こと
  （`contributorCount: 5` + `attributionNote` + `isBasedOn`）

**標準の語彙が、ちょうどこの区別のために用意されている。**

```
schema.org  creator      資料そのものの作成者
            sdPublisher  この記録を作って公開した者
                         ("the party responsible for generating and publishing
                           the current structured data markup")
            isBasedOn    元になった資料

PROV-O      prov:wasAttributedTo    TEI → 作成者たち
            prov:wasDerivedFrom     この記録 → TEI
            prov:wasAssociatedWith  アップロードという行為 → 実行者
```

Ocean の DDO には `author` しか欄が無い。曖昧なまま 1 人の名前を置くと
「1 人で作った」と読まれる。役割を明示して書く必要がある。

## 移植で踏んだ技術的な落とし穴

- **Next 16 の開発サーバは 127.0.0.1 と localhost を別オリジンとみなす。**
  片方で開くと JS が全部 403 になり、画面は出るのに何も動かない。
  **curl は Origin を送らないので 200 が返り、原因が見えない**
- ディレクトリを改名すると、プロセスの cwd は新しい名前を報告するが、
  内部の絶対パスは古いまま。`.next` ごと消して立て直す必要がある
- **viem の getLogs に生の topics を渡しても絞り込みが効かない。**
  datatoken が発行時に出す 7 種類のイベントまで数えていた。
  「どの帖も同じ 5 件」だったのが手がかり。生の RPC なら正しく 1 件
- publicnode は **複数アドレスのまとめ読みを拒否する**ようになった（以前は 100 件通った）
- **Alchemy 無料枠の eth_getLogs は 10 ブロックまで。** publicnode の 50,000 より 5,000 倍狭い。
  鍵つき RPC のほうが良いとは限らない
- Tailwind v4 は既定で node_modules を走査しない（`@source` が要る）
- next-intl は ICU を解釈するので、メッセージに山括弧を書くと落ちる
- Next 16 の proxy（旧 middleware）は Edge 非対応、OpenNext は Node の middleware 非対応。
  全ページ静的なら middleware 自体が要らない

  会社がやめれば消える。「消えない」を買うのは Arweave の ¥24
- `docs/` の静的化（SPARQL は外部の Dydra 依存、IIIF も動かない）

## DDO の項目を ○× で仕分けする (2026-08-26)

方針は 1 つ。**root から導けるものは載せない。** チェーンに置く価値があるのは
「後から言い張られたら困るもの」だけで、それ以外は費用と「訂正できない値」が増えるだけ。

きりつぼ (01.xml) の DDO は **2,725 バイト**。実測で仕分けた結果、**1,546 バイト (43% 減)**
まで落とせる。以下の「計算できる」は全部**手元で実際に再計算して一致を確認した**。

### × 落とせるもの (1,179 バイト)

| 項目 | バイト | なぜ要らないか |
|---|---|---|
| `description` | 731 | 大半が他の欄の再掲。root・CID・葉ハッシュ・証明の個数を文章で繰り返している |
| `leafHash` | 68 | `sha256(0x00 ‖ ファイルの中身)` で出る。RFC 6962 の葉の定義そのもの |
| `ipfsUri` | 68 | `ipfsCid` に `ipfs://` を足しただけ |
| `chapterRoot` | 68 | **CorpusAnchor に既に刻んである。** チェーンの別の場所にある値の写し |
| `corpusId` | 68 | 同上 |
| `tags` | 87 | 全帖で同じ 6 個 + `volume-01`。巻次から作れる |
| `author` | 30 | **個人情報。EDPB の見解では載せてはいけない** |
| `updated` | 26 | 作成時点では `created` と同じ値 |
| `volumeTitle` | 14 | `name` に入っている |
| `file` | 8 | `volumeNumber` から作れる (`01.xml`) |
| `bytes` | 5 | ファイルを数えれば出る |
| `lines` | 3 | `<seg>` を数えれば出る |

### ○ 残すもの (1,546 バイト)

| 項目 | バイト | なぜ要るか |
|---|---|---|
| `inclusionProof` | 415 | **これだけは他の 53 帖を持っていないと作れない。** DDO の存在理由 |
| `services` | 209 | Ocean の規約。datatoken のアドレスと本文の在処 |
| `ipfsCid` | 61 | **入口。** これが無いと本文に辿り着けず、上の「計算できる」も全部できない |
| `corpusAnchor` + `FromBlock` | 52 | どこを見れば root があるか。無いと第三者が走査範囲を決められない |
| `sourceCommit` | 42 | 素材のどの版か。**どこからも導けない宣言** |
| `merkleSpec` | 35 | 木の作り方。RFC 6962 か素朴な木かで root が変わる |
| `leafIndex` / `treeSize` | 3 | 証明の検算に必須 (RFC 6962 は位置と木の大きさを使う) |
| `license` | 9 | 宣言。CC0 だと言えるのは権利者だけ |

### 記事にするときの論点

1. **「導ける」には方向がある。** 本文があれば `leafHash` も `lines` も `bytes` も `ipfsCid` も
   計算できる。だが **`ipfsCid` が無いと本文が手に入らない。** 循環するので入口だけは残す。
   「何を持っている人を想定するか」を決めないと、この仕分けはできない
2. **落とすと不便になるものがある。** 一覧に「328 行」と出したければ、本文 77 KB を
   取りに行くことになる。→ **オフチェーンの索引 (`tei-facets.json`) に持たせる**。
   「証明が要る値」と「速く出したい値」は別物で、置き場所も別でよい
3. **`description` が最大の無駄 (731 バイト、全体の 27%)。** 人間向けの文章として
   書いたが、中身は機械可読な欄の再掲だった。**読みやすさのために重複を作ると、
   取り消せない場所では重複が永久に残る**
4. **43% はテストネットではタダだが、本番なら効く。** 55 件 × 1,179 バイト ≒ 64,845 バイト。
   calldata は非ゼロ 1 バイト 16 gas なので **約 104 万 gas**。20 gwei なら約 0.021 ETH
5. **仕分けの基準は 4 つの問いに落ちる** — root から導けるか / 誰が数えても同じか /
   後で直す可能性があるか / 個人情報か。**どれか 1 つでも「はい」なら載せない**
