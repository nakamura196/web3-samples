# 米切手 — 蔵屋敷の預り証を XRPL に載せる

江戸時代、諸藩は大坂に蔵屋敷を置き、国元から運ばせた年貢米をそこに納めた。
蔵元は「米○石を確かに預かった」という**米切手**を発行し、藩はそれを売って現金を得た。
切手を買った米仲買は、蔵屋敷に持ち込めばいつでも米と引き換えられる。

切手は米そのものではなく**蔵屋敷の負債**であり、「どの藩の蔵屋敷が出したか」で値が違った。
そして切手は堂島の米会所で売買され、1730 年に幕府公認となって、
世界で最初の組織的な先物市場になった。

XRP Ledger の issued currency (IOU) は、この構造をほぼそのまま持っている。
このアプリは、その米切手を **XRPL Testnet 上で実際に発行し、譲渡し、決済する**ところまでを
ブラウザだけで実行する。

題材は *Building Trust Infrastructure — From Roman Grain to XRPL*
(UBC Blockchain Summer Institute, 2026-08-21 · Mayowa Rosanwo / XRPL Canada)。
講演の例はローマ期エジプトの穀物受領証だが、日本の読み手に合わせて米切手に置き換えた。構造は同じである。

## 動かす

```
npm install
npm run dev
```

<http://localhost:3000> を開いて「① から順に実行」を押す。所要およそ 60 秒。

ページは 5 つある。

| パス | 中身 |
|---|---|
| `/` | デモ本体。6 ステップを実際に Testnet 上で実行する |
| `/easy` | はじめての人へ。専門語を前提にしない説明。たとえ話 → 6 ステップ → 出てくる言葉 |
| `/learn` | 解説。何をしているのか・普通のシステム (非 web3) との違い・他のプロトコルとの違い・よくある誤解 |
| `/apply` | 応用。プロトコル別の得意/不得意、米切手の例はどの台帳向きか、デジタルアーカイブ・学術情報流通・DH での応用、具体的なアプリ案 10 件 |
| `/glossary` | わからないとき。用語集 50 語・よくある質問 22 件と、打ち込んだ文に近いものを探す箱 |

UI を通さずヘッドレスで同じ 6 ステップを走らせる検証スクリプトもある:

```
npm run verify        # 6 ステップを Testnet 上で通す
npm run answer-check  # 質問の振り分けが壊れていないか確かめる

node scripts/no-default-ripple.ts   # ② を飛ばすと実際に何が落ちるのかを Testnet で実測する
```

## 用語と質問 — なぜ LLM を使わないか

用語の出し方は 2 通りあり、語の役割で使い分ける。

**その節の主題になる語は、本文の直後に定義ごと置く** (`KeyTerms`)。② なら `DefaultRipple` と
`rippling` がそれにあたる。講義では誰もクリックしないし、投影すればホバーもクリックも
働かない。主題の定義は、読み流すだけで目に入る場所に要る。どの語を主題とするかは
`DemoApp.tsx` の `STEPS[].keyTerms` で決める。

**たまたま出てきた語は点線付きのリンクにする** (`AutoTerms`)。クリックすると意味が出て、
「もっと詳しく」で本文、「用語集で見る」で `/glossary` へ飛ぶ。地の文には手を入れていない —
`AutoTerms` が走査し、`lib/glossary.ts` の語を長いものから順に拾う (1 段落につき同じ語は
最初の 1 箇所だけ、主題の語は重複を避けて除外)。

どちらも文言は `lib/glossary.ts` を引くので、書き分けが二重管理にならない。

### やさしい方と、正確な方

用語には 2 つの書き方を持たせてある (`lib/glossary.ts`)。

| フィールド | 使う場所 | 例 (`trustline`) |
|---|---|---|
| `plainTerm` | 常に見えている場所の見出し | 受け取る前の同意（トラストライン / 信用線） |
| `plain` | 同上の一行 | 「この人の約束の紙なら受け取ります」という事前の同意。これが無いと届かない |
| `term` / `short` | クリックした先、用語集 | トラストライン / 「この発行体のこの通貨を、上限いくらまで持つ」という受け手側の同意 |

**壁になるのは定義文ではなく、語そのものであることが多い。** 「信用線」は
知っている漢字を並べただけで意味が立ち上がらない。だから `plainTerm` では見出しごと
日常語に置き換え、本当の用語は括弧で残す — 消すと xrpl.org を読むときに困るからである。

面ごとに register を変えてあり、切り替えスイッチは無い。常に見えている場所 (本文の定義、
`/easy`) はやさしい方、クリックした先 (ポップオーバー、`/glossary`) は正確な方を出す。
トグルにしなかったのは、初めての人に要るのが同じ説明の言い換えではなく、
**順序の違う説明**だったため。`/easy` は「そもそも何の話か → たとえ話 → 6 ステップ →
出てくる言葉」という別の並びになっていて、本文は `lib/easy.ts` に分けてある。

`/glossary` の「聞いてみる」は自由入力を受けるが、**LLM は呼んでいない**。
打ち込まれた文と、用意した 50 語 + 22 件との間で文字バイグラムの重なり (Dice 係数) を測り、
一番近いものを返しているだけである (`lib/answer.ts`)。日本語は空白で語が切れないので、
形態素解析器を足す代わりにこうした。依存パッケージは増えていない。

そうした理由は 4 つある。

- **バックエンドを持たないという前提を壊さない。** ここは Testnet の鍵をブラウザ内で生成する
  アプリで、「サーバに送っていない」ことが信用の根拠になっている。LLM を呼ぶには
  Route Handler が要り、その前提が嘘になる。実際 `next build` の出力は今も全ページ static である
- **講義中に待たされない。** 回答は即座に出る。会場の回線が細くても、API が落ちていても動く
- **もっともらしい嘘が混ざらない。** 内容は固定で、受講者の前でハルシネーションが起きる余地がない
- **課金もレート制限も要らない。** 公開して受講者に配るアプリで、認証なしの LLM エンドポイントを
  晒す必要がなくなる

代償は「想定していない質問に答えられない」こと。近い答えが無いときは、そう表示して用語集へ誘導する。
10 分の演習では、想定外はその場にいる講師が答えるほうが速い。

なお講演で使われた原典のデモ (`xrpl-ubc-demo`) の Generate Code も、実体は
テンプレートへの値の差し込みと表示の演出であって、LLM は入っていない。
**「その場で組み立てているように見えること」と「その場で組み立てていること」は別で、
教材に要るのは前者だけである。**

## 図

`/easy` には図を 5 枚入れてある (`components/figures.tsx`)。素の SVG を手で書いており、
作図ライブラリは入れていない。配色はページの CSS 変数を引くので明暗どちらのテーマでも読める。

方針は 4 つ。**1 枚の図はひとつの関係だけを示す**（盛り込むと何も言わなくなる）、
**矢印には必ずラベルを付ける**（無記名の矢印は「なんか関係がある」でしかない）、
**色だけに意味を持たせない**（◯ ✕ と語で二重に示す）、
**`<figure>` + `<figcaption>` + `role="img"` + `aria-label`**（読み上げでも同じことが伝わるように）。

| 図 | 示している関係 |
|---|---|
| 米切手の流れ | 紙は「米を出した藩」ではなく「代金を払った米仲買」に渡る |
| DefaultRipple | 送金だけが `tecPATH_DRY` で落ち、板の約定は通る（実測結果） |
| 信用線 | 同意が無いと届かない / 先に同意すると届く |
| XRP とトークン | トークンには発行体の負債がぶら下がったままになる |
| TakerGets / TakerPays | 主語が「相手」なので向きを取り違えやすい |

## コードを生成

各ステップの「コードを生成」は、テンプレートに実行時の値を差し込んで 1 行ずつ出す
(`lib/codegen.ts` / `components/GeneratedCode.tsx`)。原典との違いは差し込む値で、
あちらが入れられるのはフォームに打った値だけだが、こちらは **① で実際に作られた口座の
アドレス**を入れられる。① を実行すると、表示中のコードもその場で組み立て直される。
出てきたコードはそのまま Node.js に貼れば同じことが起きる。

`prefers-reduced-motion: reduce` のときは演出を省いて一度に出す。

## 何が起きるか

| # | 操作 | XRPL の機能 | 西暦 150 年の対応 |
|---|---|---|---|
| ① | 3 者の鍵を作り faucet で入金 | `Wallet.generate` / base reserve | 蔵元・藩・米仲買がそろう |
| ② | 蔵元を発行体として設定 | `AccountSet` (DefaultRipple) | 「この蔵屋敷の切手を出す」立場になる |
| ③ | 藩と米仲買が信用線を引く | `TrustSet` | 「この蔵屋敷の切手なら受け取る」 |
| ④ | 米 100 石ぶんの切手を発行 | `Payment` (IOU) | 蔵元が印判を押して藩に渡す |
| ⑤ | 40 石ぶんを 8 XRP で売り注文 | `OfferCreate` (ネイティブ DEX) | 堂島の米会所に出す |
| ⑥ | 米仲買が 5 XRP で 25 石ぶんを取得 | `OfferCreate` (部分約定) | 米と引き換える権利が別の手に渡る |
| ⑦ | 経路を聞く (任意) | `ripple_path_find` | — |

実測 (Testnet, 2026-08-21):

```
AccountSet   tesSUCCESS  ledger=20101721  fee=12drops
TrustSet     tesSUCCESS  ledger=20101723  fee=12drops
TrustSet     tesSUCCESS  ledger=20101725  fee=12drops
Payment      tesSUCCESS  ledger=20101727  fee=12drops
OfferCreate  tesSUCCESS  ledger=20101729  fee=12drops
OfferCreate  tesSUCCESS  ledger=20101731  fee=12drops
total fee: 72 drops = 0.000072 XRP     全体 58.6 秒 (うち faucet 待ちが約 21 秒)
```

終了後の残高:

```
kuramoto  99.999976 XRP   -25 KOK, -75 KOK   ← 発行体の残高は負 = 負債
han      104.999976 XRP    75 KOK
nakagai   94.999976 XRP    25 KOK
board:  15 石ぶんを 3 XRP で (藩の売り注文の残り)
```

`ripple_path_find` は 2 通り返す — **1 XRP を出して板を経由する**か、
**5 石ぶんの切手を直接渡す**か。板の状態が変われば答えも変わる。

## 設計

**バックエンドが無い。** サーバコンポーネントは静的な文章を出すだけで、
XRPL とのやり取りはすべてブラウザから
`wss://s.altnet.rippletest.net:51233` へ直接つないでいる。
鍵はブラウザのメモリ上で生成され、どこにも送信されず、リロードで消える。
保存する場所が無いので、漏れる場所も無い。

```
src/
  lib/ledger.ts      接続・残高・板・経路探索 (読み取り側)
  lib/scenario.ts    6 ステップのシナリオ (書き込み側)
  components/        UI
  app/page.tsx       デモ本体 (静的な文章 + クライアントコンポーネント)
  app/learn/page.tsx 解説ページ (完全に静的。クライアント JS を持たない)
  app/apply/page.tsx 応用ページ (同上)
  components/learn.tsx  解説ページ用の表示部品
  components/apply.tsx  応用ページ用の表示部品
scripts/e2e.ts       ヘッドレス検証 (npm run verify)
```

`lib/scenario.ts` は React に依存していない。だから同じコードが
ブラウザでも `npm run verify` でも動き、「ブラウザの問題か XRPL の問題か」を切り分けられる。

## 踏んだ地雷

- **DefaultRipple を立て忘れる**。落ちるのは**保有者どうしの `Payment`** で、`tecPATH_DRY` が返る。
  当初この README には「⑥ の約定が落ちる」と書いていたが、**これは誤りだった**。
  Testnet で実測したところ (`npm run answer-check` ではなく `node scripts/no-default-ripple.ts`)、
  DefaultRipple が無くても ④ 発行・⑤ 注文・⑥ 約定はすべて `tesSUCCESS` で通る。
  板の約定は rippling を経由しないためで、`OfferCreate` の公式エラー一覧に `tecPATH_DRY` は無い。
  **つまりこの 6 ステップは ② を飛ばしても完走してしまう。**
  漏れが表に出るのは、発行したトークンを人から人へ送ろうとした本番の場面である。
- **信用線が無い口座に IOU は届かない**。`Payment` は `tecPATH_DRY` で失敗し、
  失敗が台帳に記録され手数料も焼かれる。ただし DEX で買った場合は信用線が暗黙に作られる。
- **`tec` 系のエラーは手数料を消費して台帳に載る**。「失敗した」という記録が残る。
  `tem` 系はそもそも不正形で、台帳には載らない。
- **`OfferCreate` の `TakerGets` / `TakerPays` は注文の作成者から見た向き**。
  `TakerGets` = 作成者が売るもの。取り違えると逆の注文が出る。
- 発行体の `account_lines` は保有者ごとに 1 行ずつ返る。
  上の残高表示で `-25 KOK, -75 KOK` と 2 行あるのは、米仲買と藩に分かれて負債を負っているから。

## XRPL の特徴 (このデモで触れた範囲)

- **マイニングをしない合意形成** — validator が投票を重ね、80% を超えた時点でレジャーが閉じる。
  消費するのは電力ではなく帯域。
- **3〜5 秒で決定的ファイナリティ** — 確率的ではなく決定的なので「6 ブロック待って確信を高める」
  手続きが無い。ただし検証済み (validated) レジャーに入るまでの 3〜5 秒は待つ。
  `submit` が返す `tesSUCCESS` は暫定値で、最終なのは validated に入った時点。
  このデモは `submitAndWait` を使っているので画面の `tesSUCCESS` は最終である。
  なお「フォークが絶対に起きない」わけでもなく、UNL の重なりが不足すれば分岐しうるとドキュメントは明記している。
- **UNL** — 「どの validator の声を聞くか」を各サーバが選ぶ。学術論文の引用リストに近い。
- **発行体は資産の一部** — 「A 藩の蔵屋敷の 100 石」と「B 藩の蔵屋敷の 100 石」は別の資産。
- **信用線** — 保有には受け手の同意が要る。与信管理がプロトコル層にある。
- **DEX / AMM がプロトコルの一次機能** — 2012 年から `OfferCreate` がある。デプロイも監査予算も不要。
- **準備金** — 口座 1 XRP + オブジェクト 1 件ごと 0.2 XRP。台帳肥大への課金。
- **アムンドメント** — 機能追加は validator の 80% 支持が 2 週間続いて初めて有効になる。

諦めているものもある。速さと安さは、**「UNL の validator が結託しない」という賭け**を
引き受けた対価であり、PoW が電力で買っているものとは前提が違う。
汎用スマートコントラクトも無い。そして IOU はどこまでいっても発行体の負債で、
蔵が焼ければ切手はただの紙になる — 台帳が保証するのは「誰が何を負ったか」の記録だけである。
