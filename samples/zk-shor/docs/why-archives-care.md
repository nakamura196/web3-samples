# なぜアーカイブがこれを気にするのか

暗号の話に見えて、実は**証拠の寿命**の話である。

## 1. 署名の証拠能力は、暗号の困難性を借りている

紙の記録が証拠になるのは、来歴・保管の連鎖・第三者の証言といった
**複数の独立した根拠**が重なるからである。どれか1つが崩れても全体は残る。

デジタル署名はそうなっていない。「この文書は本人が承認した」という主張は、
最終的に**たった1つの数学的仮定**に載っている。

```
y = g^x から x を求めるのは難しい
```

この行が成り立つ限り、署名は本人しか作れない。成り立たなくなった瞬間、
**過去に作られた署名も含めて**、誰でも作れるものになる。

`zkshor shor` はこの「成り立たなくなった瞬間」を、玩具サイズで再現する。

## 2. 遡及的に壊れる

ここが普通のセキュリティ事故と違う。

サーバが侵入されたなら、侵入前の記録は無事である。時点で切れる。
暗号の仮定が崩れる場合、**切れ目がない**。2026 年に作られた署名は、
2050 年に検証しても「正しい署名」として通る。ただしその頃には、
2050 年の誰かが同じものを作れる。

検証者から見て、この2つは**区別できない**。署名は署名でしかなく、
「いつ作られたか」を自分では主張しない。

つまり、いま集めている電子署名付きの記録は、**将来のある時点で
一斉に証拠能力を失う**可能性を持っている。個別に壊れるのではなく、
一斉に。

## 3. 保存しているほど危ない

`zkshor ledger` が示すのはこれである。

ブロックチェーンは「消えないこと」を長所として設計されている。
XRPL のアドレスは公開鍵のハッシュなので、送金するまで鍵は隠れている。
しかし一度送金すれば、公開鍵は台帳に載り、二度と消えない。

攻撃者がすべきことは**待つことだけ**である。今日の台帳をコピーして
保存しておく。侵入も権限も要らない。公開情報を読むだけである。
量子計算機が手に入った日に、保存しておいた公開鍵から秘密鍵を再構成する。

**harvest now, forge later**。暗号文に対する
"harvest now, decrypt later" の署名版で、性質が悪い点が1つある。
復号は「読まれる」だけだが、署名の偽造は**新しい記録を作れる**。

そしてアーカイブ機関が「改竄検知のため」に台帳を長期保存するとき、
同時にこの攻撃材料の表も保存していることになる。長期保存の営みそのものが、
将来の攻撃面を育てる。

## 4. IIIF / 来歴記録に引き寄せると

アノテーションの帰属を電子署名で担保する設計を考える。
「この注釈は誰某が 2026 年に付けた」を署名で示す。

この設計は、次の条件が揃うと破綻する。

- 署名鍵の公開鍵が記録と一緒に保存されている (当然そうする)
- 保存期間が暗号の寿命より長い (アーカイブなら当然そうなる)
- 署名だけが帰属の根拠になっている (単純に作るとそうなる)

3番目だけが設計者の裁量である。だから対策もそこにしかない。

## 5. では何をするか

暗号の側でできること:

- **耐量子署名に移る** — NIST FIPS 204 (ML-DSA) / FIPS 205 (SLH-DSA)。
  特に SLH-DSA はハッシュだけに依存するので、Shor が効かない
- **重ねる (hybrid)** — 従来署名と耐量子署名を両方付ける。
  移行期はこれが現実的
- **鍵を晒さない** — 使い回さない、公開鍵をアーカイブに焼き込まない

暗号だけでは閉じない部分:

- **信頼できるタイムスタンプ** — 「その署名がいつ存在したか」を
  独立に固定する。RFC 3161 や、新聞の紙面に載せる類のもの。
  署名自体が壊れても「壊れる前に存在した」は残せる
- **証拠を重ねる** — 署名、来歴記録、第三者の保管、公開の記録。
  1つの数学的仮定に全部を賭けない
- **再署名の運用** — 定期的に、当時有効な方式で署名し直す。
  ただし「誰がいつ再署名したか」の記録が新たに要る
- **アーカイブの作法に戻す** — 上の3つは、結局のところ
  紙の時代からの標準的な手当てである

## 6. この教材が言いたいこと

「量子計算機が来ると暗号が破れる」は、抽象的なうちは行動に繋がらない。

`zkshor` は、破れる瞬間を**実際に走らせて見せる**。玩具サイズだが、
数式もアルゴリズムも本番と同じである。パラメータを大きくすれば
そのまま実運用の Schnorr になり、Shor の側は動かなくなる ——
それは Shor が弱いからではなく、古典計算機でシミュレートできないからである。

このコードを一度でも自分で書くと、次の3つが体感として分かれる。

1. **プロトコルの正しさ**と**仮定の妥当性**は別物である
2. 仮定は、**あとから**壊れる
3. だから証拠は、**1つの仮定に載せてはいけない**

3 は、アーカイブ学がずっと言ってきたことである。
